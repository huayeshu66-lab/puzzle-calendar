# 可选图形答案二维码：Cloudflare Pages

仅在用户选择联网图形答案时使用。目标是普通扫码即见对应题目的完整答案图，并可打开原图或下载；无需专用读取器。用户选纸质答案时跳过整个流程。已有可用网站时可以复用，不强制采用 Cloudflare。

## 1. 沿用选择，准备答案

- 确认用户接受通过链接公开访问答案，并明确主要扫码软件与使用网络；已知选择和发布授权直接沿用。
- 使用当前用户自己的 Cloudflare 账户。需要时由用户注册、登录；助手承担文件准备、上传和发布。无需先创建远程代码仓库或购买域名。
- 从冻结题目与已验证解导出 PNG 等答案图，逐题核对原有线索、解答标记、日期和题型。只发布选定范围的答案及网页所需文件。
- 在任务制作资料中保存日期、题目ID、答案文件及哈希的对应表。按题量 N 规划；闰年、多题一天和子集交付不能套用固定365题。

## 2. 准备轻量静态站点

页面直接显示答案图，并提供“查看原图”“下载图片”。保持手机可读，不添加与使用无关的标题、平台说明或诊断信息。规则仍按用户选定的载体提供；符号含义不清时给必要图例。

全年可共用一个查看页，通过日期或稳定题目ID选图，例如 `/?date=2027-01-01`。同一天多题时增加唯一题目键。查看页只接受当前任务映射内的键；缺失、无效或尚未发布的日期显示“暂无该日答案”，不能回退为另一题。单题样页可直接显示一张图。

一种适合后台直接上传的目录结构：

```text
site/
  index.html                 # 共用查看页，可内嵌日期映射和样式
  404.html
  _headers
  answers/                   # 每题一张答案图
  download/                  # 需要附件下载时，放相同图片副本
```

查看和下载文件保持相同内容。下载链接指向 `download/`，可加 HTML `download` 属性，并在 `_headers` 使用一条通配规则：

```text
/download/*
  Content-Disposition: attachment
  Content-Type: image/png
```

上述类型用于纯 PNG 目录；混合格式时按实际类型设置。附件响应头用于请求下载，微信是否保存到相册仍由客户端决定。可在折叠帮助中提供“打开原图后长按保存／用浏览器打开”，不承诺自动入相册。

把 `site/` 内的内容打成 ZIP，使 `index.html` 位于压缩包根目录。发布包不含凭据、Git文件、内部记录、源题库或未授权内容；二维码图片保留在本地制作资料及PDF中，无需上传。

### 容量规划

二维码本地生成没有平台按张计数的配额；实际约束是网站文件数、单文件大小和上传方法。下列额度于2026-10-23核对，执行时重查官方文档：

| 项目 | 额度／计算 |
| --- | --- |
| Pages 免费站点 | 最多20,000个文件；单文件最大25 MiB |
| 控制台拖放上传 | 最多1,000个文件；Wrangler可上传20,000个 |
| `_headers` | 最多100条规则；下载使用通配规则，不为每题写一条 |
| 共用页 + 原图/下载副本 + 404 + headers | `2N+3`个文件；365题为733个，366题为735个 |

独立JS、样式、索引或规则资料也计入总文件数。若每天另做HTML并保留两份图，365题加404和headers为1,097个，超出后台上传上限；可共用查看页，或改用用户已授权的Wrangler上传。同一项目可以使用这两种Direct Upload方法。文件数和图片体积都以最终包实测为准，免费额度不作永久承诺。

## 3. 在用户账户中发布

1. 在用户已登录的浏览器打开 Cloudflare，进入 **Workers & Pages**；新建 **Pages / Direct Upload** 项目，选择上传文件／拖放ZIP。已有对应项目则创建新部署。界面名称可能变化，依据当前可见页面操作。
2. 上传准备好的ZIP，核对文件数量和错误提示，再部署到生产地址。准备与上传由助手执行；只有登录或工具无法执行的具体步骤才交给用户。
3. 读取Cloudflare实际返回的正式 `pages.dev` 地址，保存到当前任务。不要猜域名或使用临时预览、登录、含令牌的地址。无需为每个二维码创建一个网站。
4. 匿名访问页面、原图及下载路径；核对图像内容与冻结答案哈希，确认没有登录拦截，下载路径返回附件响应头。

使用当前可用的浏览器／部署工具及其文档，不依赖历史标签ID、内部接口或会话。工具超时时先核对当前部署状态，避免重复提交；若仍不能操作，明确具体阻塞点并交付准备好的包和剩余一步。

## 4. 生成并验证二维码

- 用正式站点地址及每题固定路径／参数在本地批量编码。可使用现有二维码库，例如ReportLab；不需要付费动态码平台。直接看原图的用户则编码对应图片URL。
- 先用代表样例在目标网络和扫码软件上验证完整答案显示，再批量排入日历。二维码配色、尺寸和页面融入方式按 [答案与玩法交付](answer-and-rules.md#可选二维码) 处理。
- 对最终PDF逐码解码，与日期—题目—答案URL映射逐一比对；核对全部答案资源存在且内容匹配，额外检查手机显示及无效日期处理。用户需要下载时，单独验证保存体验。
- 按实际尺寸试印扫码，分开记录本地解码、线上内容、目标手机、保存和纸上扫码结果。一张样例通过不等于全年全部通过。

印刷前固定每题URL，后续更新同一项目时保留这些路径和参数；保留完整站点源文件与映射，分月更新不能覆盖丢失旧月份。二维码本身无需续费，但链接依赖站点持续可用；若迁移应保留原入口。测试站点和当前用户账户信息只存于该任务，不写进技能默认值或别人的日历。

## 5. 按选择交付

仅选二维码时，基线生成的独立答案PDF可留在内部制作资料用于核对；用户包另组为含二维码的日历及所选规则资料。用户同时要纸质答案时才交付相应答案PDF。站点源文件、映射及维护说明单独交给站点所有者，便于后续保留入口和更新。

线上内容、目标手机、下载保存及试印证据绑定当前答案文件哈希与正式URL，登记为任务design制作资料。现有release的ready状态不覆盖这些检查；未验证项明确保留为待测，不能据此宣称二维码交付全部完成。
