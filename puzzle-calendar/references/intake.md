# 从使用情境到制作简报

## 先判断用户要解决什么

先从现有对话、任务文件和成品提取已知信息。第一次不要抛出几十个配置字段；用少量自然语言问题建立设计依据：

> 这份日历给谁、准备放在哪里或怎样使用？你最希望它做到哪两三点？
> 想做哪个日期范围，先看少量样页还是已有明确方案？
> 有什么打印和装订条件？不知道的细节可以由我推荐。

这些只是缺信息时的例子。日期、对象、黑白打印等已知就不再问；较晚的样稿说明把已明确的需求写成“建议”时，以用户原话为准，不回退成未知。用户要求制作整月与用户选定具体风格是不同的决定。不要把“创建skill”当成用户正在订制某年份日历。

根据使用情境继续必要分支：儿童补年龄与阅读能力；大字需求补可读性；独立撕页明确能否单张理解玩法；自用连续翻阅可把完整规则另附。产品是桌历、挂历、月计划还是每日解谜，不能只根据名称决定每页内容。未实现的工艺或组合先核实再承诺。

## 让模型承担判断，用户决定有意义的取舍

收集日期、出题节奏、受众与难度目标、打印纸与成品、单双面／装订、答案与输出形式。先问“你希望怎样用”，再转换成对应技术字段；不要让用户知道字号、SVG或规则策略代码才会下单。

答案放在哪里与玩法怎样提供是两组选项，分别沿用用户选择，不绑定成一套。先让用户选择纸质答案、扫码查看或两者兼有，也接受自定方案；不默认加二维码。可选项见 [答案与玩法交付](answer-and-rules.md)。只有选择二维码后，才补问想看图形答案、文字还是解题步骤，以及是否接受联网查看页／原图链接；已有选择直接沿用。

选联网二维码时补齐使用地网络、主要扫码软件和用户可用的托管位置。没有现成网站时，可推荐 [Cloudflare Pages 免费静态托管流程](qr-cloudflare.md)：用户使用自己的账户登录，助手准备并上传答案站点；不要求用户先有代码仓库或购买域名。说明答案将经链接公开访问，按已有授权继续；登录、密码和验证码由用户自行处理。用户有合适的网站时直接复用，不强制更换平台。

附加信息按用户目标选择：传统历法与节庆、寄语与知识、运势、随手记空间或专用跟踪等。没有选择就不默认全部开启；选定某类后才补必要细节。出生资料只在实际选定个人排盘时需要。历法与出处核对见 [信息模块](calendar-information.md)。

将冲突说成结果上的取舍，例如：“保留大棋盘就需要缩短寄语，长解释可以另附”；不要悄悄缩字、改难度、少出题或丢用户已选内容。能在授权范围内通过重排解决时直接做。

日期范围没有默认值；相对年份按当前时间及时区解析并保存绝对日期。其余非关键项可以推荐，记录为assumed；用户明确交由你决定才记delegated。用户明确给出的值记user，计算或设计推导记derived。沉默不自动变成批准。

## 制作简报必须有判断

`brief` 是设计理由，不是用户问卷或样式名称清单。至少说明：

- `use_case`：在哪里、由谁、以什么方式连续使用。
- `priorities`：排序后的目标；出现空间冲突时据此取舍。
- `rationale`：为什么当前方案适合这些目标。
- `regions`：日期、题面、规则、可选信息和书写区的关系；不用先写死所有毫米值。
- `tradeoffs`：保留了什么、减少了什么，以及是否仍有未知。

例：成人桌边每日一题、家用黑白打印，优先方便落笔和日期易查；大日号帮助定位，完整玩法集中到手册，日页把主要面积留给题面，寄语限短句。这个判断适用于该任务，不是所有日历的统一风格。

用户明确要求长寄语、彩色满版或单页独立使用时，重新设计相应关系。不能拿既有样页的“白底／三字体／竖排星期／20mm孔区”当作拒绝其他方案的通用规则。

## 书写空间与专用记录

把“用途”和“外观”分开：

| 用途 | 含义与用户用语 | 设计处理 |
| --- | --- | --- |
| 视觉留白 | 分隔、呼吸与对齐所需的空白 | 不据此承诺有专门可写区；装订净空也不算手写空间 |
| 普通随手记 | 像普通日历一样写备忘、日程或任意短记 | 可标“随手记／备忘”，也可不加标题；按版式安排，不以启用“记录功能”为前提 |
| 专用记录／跟踪 | 解题用时、卡点、完成勾选、习惯打卡或月度解题回顾 | 明确用途与字段后再加，标题写清主题，不笼统叫“记录” |

空白、横线、点阵或表格是书写区外观；随手记可以划线，解题草稿也可以不划线，不能用有没有线判断功能。用户只说“留点地方记事／留备注栏”时按普通随手记处理，不自动加用时、完成率或卡点。只说“留白多一点”通常是构图反馈，不自动增设表单。

普通周安排与月历备忘仍是日历书写；有题意提示的推演区标“解题草稿”，有用时或完成字段的区域标“解题记录／解题跟踪”。在brief.regions里分别说明用途、外观与有效可写范围，不把这些当作已实现的新CLI参数或information kind。

## 不知道风格时

“不知道”不是阻塞项，也不要求用户解释设计术语或先提供参考图。先沿用纸幅、黑白／彩色、受众、内容模块、装订和答案安排等已知条件；只补会影响结果的缺口。用“看图找偏好 → 拆解反馈 → 定向调整 → 真实样页确认”收敛，明确偏好或已经选定时直接从相应阶段继续。

### 用图帮助表达偏好

根据用途推荐少量差异明显的方向，必要时先展示已核实的参考或标明用途的概念图，再用同日、同题、同信息、同纸幅做比较样页。数量按探索需要，不把所有题型乘所有风格。候选应在构图、插画／纹样手法、字体角色及题盘处理上形成可辨区别；未知风格时不能给出一组只有颜色不同的极简模板。可以推荐一个起点，也允许混搭、全部不喜欢或重新选主题，不把当前候选变成风格边界。

用户要求“大众喜欢／主流”时，查可核实的品牌系列、畅销榜或实际反馈，记录来源、时间及榜单覆盖的人群／渠道。将其作为选候选的依据，不能把单品牌排行或在售产品说成全体大众偏好，更不能因此跳过用户选择。借鉴设计原则，字体、素材与受欢迎程度不凭空猜测。

结合用户看到的图，按需要问清以下维度；不一次抛出完整问卷，已表达或已委托的部分不再问：

| 维度 | 自然语言问法 | 转成什么设计判断 |
| --- | --- | --- |
| 繁简程度 | 更喜欢清爽、适中，还是丰富一点？ | 主视觉与信息的占比、黑白／色块关系、留白和装饰密度；不等于主题或风格名称 |
| 气质与主题 | 想要亲切、有趣、安静、典雅，还是酷一点？ | 选择相容的图像语言、题材和构图；不要求用户知道专业流派 |
| 具体喜欢的部分 | 这张喜欢的是插画、构图、字体、颜色，还是题盘？ | 分清保留项与待调整项，避免把局部赞同扩大成整页认可 |
| 题盘参与程度 | 网格、浅底色、数字和外框要不要一起随主题设计？ | 可以保持标准题盘、轻微调整线条与外框，或整体协调线条、底色、字面、节点与轮廓；不改变规则语义 |

配色是一条独立比较轴：试橙底或雾霭蓝不自动选择某套构图，也不把原来已确认的黑白打印改成彩色。选“题盘一起设计”同样只确认处理幅度，未同时确认的主题、配色和候选仍待定。黑白稿按线重、疏密、浅灰和正负形设计；底色与纹样须保持线索、规则标记及铅笔落笔清楚。

### 将反馈转成下一轮设计

保存用户原话，并在当前 brief 中说明已明确、否定与待定的部分，不另造一份相互冲突的需求表。例如“有特色，但装饰适中，题盘也一起设计”是本项目的设计要求，不能成为所有用户的默认偏好。

“太繁”时重排视觉重点与留白，“没特色”时重选主视觉、主题关系或表现手法；不能只从极繁稿删除图案，或往简单稿里堆饰。要求适中时仍应有完整构图和风格，题盘不能成为与页面无关的标准表格。具体评审见 [繁简与主题共同设计](design-review.md#繁简与主题共同设计)。

每轮集中解决主要未决项，保留已认可的部分和未换题的内容；比较时说明改了哪里，不因局部反馈反复重开所有方向。若候选都不合适，回到主题与构图重新选，不强迫用户从旧方案里挑。图形质量不足时重新取参考或制作素材，不能用更多装饰遮掩。

### 用真实样页明确选定范围

方向接近后，用目标纸幅与实际渲染方式做少量代表样页：准确年月日／星期、已验解题目、当前字体与底色，以及用户选定的答案安排。答案在背面时提供对应正反面；有多题型或外部线索风险时补能代表这些差异的页面，不把一张数独的适配自动推广到全年。概念PNG和生成的题盘只用于视觉探索，不能当作已验证样页。

在仍有实质未决风格时，将可审阅的当前样页与简短选择摘要一起提供，再问：“就按这套构图、字体、配色和题盘处理继续制作，还是有哪一处要改？”摘要说明候选版本／文件、确认的设计部分、保留的修改项，以及本次是认可方向、授权当前范围制作还是最终验收；不用让用户批准技术字段。

| 用户反馈 | 当前含义与下一步 |
| --- | --- |
| “你推荐”“都试试”“换个蓝试试” | 探索或推荐授权；制作可比较的候选，不填已选定 |
| “B舒服一点”“还可以”“比之前好”“这个有趣” | 记录方向改善或局部偏好；结合上下文拆解待改项，不自动定稿 |
| “用B的纹样配D的日期” | 执行明确的组合修改；确认范围只覆盖所指部分，其他未知项不冒充已选 |
| “就用这款”“按这个继续制作” | 指向当前明确版本时，记录选定及继续范围并推进，不要求重复说确认口令 |
| “风格你定，不用再确认，直接做整月” | 在委托范围内自主定稿与制作，仍做必要内容／PDF检查；不记为用户已目视认可 |

这些是解释边界，不是关键词分类器；结合正在回答的问题、指向的样稿与完整上下文判断。“同意”若是在批准修改 skill，就不是在选定日历风格。未回复不等于认可，已有明确选定和继续授权不增加重复审批。只对新出现的实质变化再确认；风格确认、最终成品验收、实物试印和真人难度分别记录。

比较组在制作资料保存共同日期／题目、候选及版本、整页与近景、输出类别、推荐理由、真实反馈、选定范围与待改项。它们是同一内容的替代设计，正式账本只计一次；参考图和当前题盘处理一并保存，避免换配色时退回旧题面。沿用现有 job／brief 与真实审阅记录，不把这些描述冒充新增CLI能力。完整检查见 [设计评审](design-review.md)。

## 单一记录源与范围

需求只在 `job.json.request.requirements` 保存一次。`decisions` 只保存相应字段的origin和reason，不再重复value；`constraints.locked` 记录不能自行改变的字段，`excluded_types` 记录排除项。scope只表示当前交付子范围，不改全年计划的题位身份。

| 需求组 | v2字段与含义 |
| --- | --- |
| 日期与节奏 | date_range、calendar_form、cadence、puzzles_per_slot、week_start |
| 使用对象 | audience、difficulty；详细目标保存在brief |
| 打印 | print.paper、orientation、mode、duplex、binding.edge／reserve_mm |
| 交付 | output.formats、output.answers；当前支持见runtime |
| 内容组织 | instructions、information.kinds、appearance |
| 当前子范围 | request.scope.start／end；未指定时为完整date_range |

通过init接收需求与简报，通过prepare导出既有planner、信息和renderer输入。不要把带requirements包装的完整任务直接塞给只接受扁平date_range的旧planner，也不要独立维护多个“最新版需求”。精确合同与CLI见 [workflow.md](workflow.md) 与 [runtime.md](runtime.md)。

## 修改按影响传播

| 修改 | 重新处理 | 保留 |
| --- | --- | --- |
| 字体、颜色、日期组或局部文字 | 受影响页面布局、实际导出、PDF和视觉检查、当前预览 | 未换题的题面、答案、ID、seed、日期 |
| 指定题目 | 该题新鲜验解、唯一性、全局去重、答案映射和相关页 | 其他已认可题目 |
| 日期范围、形式、频率 | 日期计划、题量与题位归属、受影响的派题与内容 | 仍兼容的内容记录 |
| 纸幅、方向、装订、大字、模块 | 可用空间、fit_matrix和受影响模板 | 仍适配的题目，直到明确需要换题 |
| 文件打包或说明 | 受影响交付资料、角色清单与哈希 | 内容和未改变的PDF证据 |

用revise保存变更原因与影响，不把局部反馈当成全流程重做。新文件变更后，相关旧证据失效；不受影响且哈希一致的源证明可复用，最终审阅仍要匹配当前需求／brief、scope及输出哈希。
